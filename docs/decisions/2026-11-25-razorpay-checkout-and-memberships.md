# Kiwe Razorpay, checkout and memberships

25 November 2026 · Version 1.x

## Architecture decision

Keep WooCommerce as the commerce engine. It owns product and variation prices, cart and customer sessions, tax, shipping, coupons, stock, orders, payment status and refunds. Kiwe owns the storefront, Start and Bricks authoring contracts, the checkout sheet and the presentation of native checkout data. Keep Razorpay's official WooCommerce plugin as the gateway. The Razorpay App in Kiwe gives authorized store managers and MCP clients local configuration status. The site administrator or Kiwe owner configures payments in native WooCommerce settings. Provision the official gateway for eligible new sites with payments disabled until the site's merchant configuration is ready. [WooCommerce Store API checkout](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/checkout/) · [Razorpay's WooCommerce integration](https://razorpay.com/app-store/woocommerce/)

This choice retains the transaction and operational contracts current Kiwe stores already use. For a faster experience, start with the requests, assets and steps on the shopper's path. Use compatible HPOS on stores where plugin and recovery checks pass, keep public pages cacheable, and keep personalized checkout, cart and account responses private. Measure server work, assets, input readiness and the provider handoff independently. Revisit an alternate commerce engine only if representative measurements identify a remaining WooCommerce bottleneck and the replacement can preserve the same inventory, tax, fulfillment, refund and recovery behavior. [HPOS technical documentation](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/) · [WooCommerce store speed guidance](https://woocommerce.com/posts/speed-up-your-woocommerce-store/)

The reviewed WordPress.org Razorpay 4.8.9 archive matched all 440 published file hashes. It declares HPOS and Checkout Blocks support and its header lists WooCommerce 10.6.2 as the tested version. The standard Woo gateway returns a same-origin WooCommerce order-pay URL. Its receipt loads Razorpay Checkout. It also enqueues the SDK on the initial checkout route. Kiwe's existing Store gateway asset service removes a duplicate SDK on a qualified receipt path. Kiwe's method adapter adds a documented Razorpay display configuration to that exact gateway's native standard receipt when the merchant enables it. Ordinary WooCommerce orders, payment verification and refunds stay with the official gateway. [Download and release details](https://wordpress.org/plugins/woo-razorpay/) · [Razorpay display configuration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/configure-payment-methods)

## Checkout experience

1. Use the accepted Kiwe checkout draft to show the shopper's address and contact details alongside an itemized WooCommerce order summary. Edit or add an address through the existing sheet. Keep the native checkout form reachable through the same page. A successful save uses the Woo session, updates the native fields and recalculates shipping and taxes in WooCommerce. Saved-cart capture continues through its existing checkout draft hook.
2. Kiwe's classic checkout option shows the address summary and quick payment choices beside the native WooCommerce totals and coupon controls. The controls follow the gateways available to the current cart. The Bricks shortcode path restores the native coupon form when Bricks has reserved it for its own separate coupon element. Bricks-native coupon templates keep their existing controls.
3. For direct payment, verify a supported Razorpay checkout configuration per selected method. Pass the exact WooCommerce order, amount and currency into the provider flow. The shopper chooses the method on the Kiwe page, then completes bank or app authorization through Razorpay's supported UI. Keep card data in the provider-owned UI. Preserve native order-pay as the recovery route if the provider, payment method or device needs it. Verify the signed payment and reconcile status on the same order after a timeout, retry, reload or delayed notification. [Razorpay payment-method configuration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/configure-payment-methods) · [WooCommerce Checkout Block payment flow](https://developer.woocommerce.com/docs/block-development/extensible-blocks/cart-and-checkout-blocks/checkout-payment-methods/checkout-flow-and-events/)
4. Rehearse a cold phone visit, slow or interrupted draft save, native form fallback, validation failure, back navigation, return from the provider, duplicate submission, failed or expired payment, paid callback, refund and COD. Validate pricing and stock before each payable attempt. The buyer can resume a saved draft and pending order when connected.

For an authored classic checkout, use [the native checkout-details link](#checkout-details-attribute) at the address summary.

### Checkout details attribute

Use the link on the real, editable WooCommerce checkout page, where the native checkout form contains the #customer_details destination. Kiwe opens the checkout sheet and returns the saved details to the same form.

~~~html
<a href="#customer_details" data-kiwe-checkout-details>Edit checkout details</a>
~~~

## Membership and recurring products

Kiwe owns the recurring-product, billing-agreement and member-access integrations. Bricks is the only required paid plugin license. WooCommerce core owns native products, variations, prices, carts, coupons, stock, shipping, initial orders and renewal order records. Razorpay Subscriptions handles mandate authorization and scheduled charges through its API. The existing Kiwe Launch billing service provides the tested precedent for paid invoices, renewal consent and refund reconciliation. Membership access follows verified paid periods. [Razorpay subscription API](https://razorpay.com/docs/api/payments/subscriptions/create-subscription) · [Razorpay subscription webhooks](https://razorpay.com/docs/payments/subscriptions/webhooks/)

- In Start, record whether the website needs ecommerce, membership, or both. Existing content or service sites can keep both capabilities off. The human selects the desired capabilities. The provisioning request proposes the matching App set. Installed capability and verified readiness control which flows are available.
- Keep site activity and the public design brief in the native WordPress Design Context. Start and MCP read the saved capabilities and approved public facts. A generator can propose a plan comparison, joining page, member account and product catalogue that fit those facts. A design request can suggest an App without installing or enabling payment methods.
- In **Store → Products**, use **Billing** in a simple product or **Variations → Pricing** for each variation. The owner can choose one-time or recurring billing and enter the price at checkout, the length of the first paid term and the price and interval for renewal. WooCommerce continues to use the same product and variation types. Different variations can use different billing modes. Draft terms are available in the same Store authoring records through MCP. The current pilot accepts INR and virtual recurring items. Keep their public purchase blocked until the billing integration is complete.
- For mixed carts, calculate the initial payable amount with WooCommerce and collect it through the native transaction path. Only recurring lines contribute to the renewal quote. The first adapter requires a common first term and renewal interval across recurring lines in one order. A subscription entry should freeze the consented product terms on that order so later catalog edits leave an existing agreement intact. Razorpay's paid invoice and captured payment must agree on amount, currency, subscription and period before Kiwe creates one renewal order and advances paid access.
- A membership binding attaches access to the paid product and customer account. Keep IDs, ledger currency, paid-through dates and provider references portable. Handle retries, idempotent receipts, disputes, refunds, holds, cancellation at term end, expiry and recovery. A future merchant can map the agreement to another verified provider and request fresh customer consent where required.

## Scaling and moving to another runtime

WordPress, PHP and MySQL remain the first operating tier. Choose a different runtime when consistent measurements show that the site's latency, traffic peaks, workload or operating cost warrant it. Use edge caching for public pages, tune PHP workers and persistent object caching, qualify HPOS and database indexes, and move bounded background work off checkout. Measure visits, carts and concurrent purchases separately. A language change alone does not remove shipping, database, payment-provider or mobile network delays. [WordPress performance guide](https://developer.wordpress.org/advanced-administration/performance/optimization/) · [WooCommerce scaling guide](https://developer.woocommerce.com/2024/08/22/scaling-with-woocommerce/)

The next tier can move public rendering, media or search while keeping WordPress and WooCommerce as the authoring and transaction systems. Kiwe Start, the user-facing dashboard and MCP should speak the same documented site and commerce operations across tiers. Keep the WordPress adapter concrete today. Add another adapter when there is a qualified second implementation. [WordPress REST API](https://developer.wordpress.org/rest-api/)

An **Upscale** action should prepare a destination, migrate and verify a copy, and present the exact changes and cutover for review. Keep the Kiwe project and tenant identity, site and page routes, customer and role mappings, catalogue and stock, order and payment history, verified membership periods, public content, media, accepted Seam source and Design Context. Keep an encrypted native recovery copy and a versioned export of equivalent records for a new runtime. The destination can use its own database schema. Check which identities, payment mandates and saved methods can move under the same merchant and provider, and collect fresh consent or re-link where the provider requires it. [Current Kiwe recovery runbook](../CORE-FLEET-RELEASE.md#verification-and-recovery) · [Razorpay tokenized saved cards](https://razorpay.com/docs/payments/payment-methods/cards/features/saved-cards/)

During cutover, reconcile the last order, stock and payment changes from the old site, verify the new site with the same customer and admin tasks, and keep one authoritative writer. Include tested recovery for new transactions after the switch. Present the same Kiwe dashboard and capabilities at the destination as each adapter qualifies. The operational goal is one guided upgrade experience with continuity for the client.

## Local qualification

The isolated Kiwe Launch fixture used WordPress 7.1.5, Twenty Twenty-Five, WooCommerce 11.3.1 and the Razorpay 4.8.9 archive. PHP served loopback traffic without a page cache. Each value is the median of 11 sequential HTML requests after three warmups. Checkout used a guest cart with one virtual product.

| Active commerce plugins | Home HTML | Classic checkout HTML | Razorpay SDK referenced on checkout |
| --- | ---: | ---: | --- |
| Kiwe with WooCommerce inactive | 391 ms | — | — |
| WooCommerce | 785 ms | 755 ms | No |
| WooCommerce and Razorpay | 821 ms | 808 ms | Yes |

This measures response completion through the local server. The comparison excludes downloading or running external scripts, payment processing, cold mobile traffic and concurrent load. The home HTML contained no Razorpay SDK reference in all three runs. The timings identify a useful next measurement on an actual storefront. They leave production conversion, provider latency and the impact of a different commerce engine open.

Fifteen native checks verified the App and MCP status, permission gates, settings link and omission of keys. A 390 px touch viewport verified first-tap editing, one checkout details read and zero extra cart reads per edit. A stalled request and an injected 503 left the native checkout form reachable. The native anchor worked with JavaScript off. The synthetic cash-on-delivery purchase reached the WooCommerce receipt and native order readback confirmed the saved details and ₹199 processing order.

The Bricks pilot uses the classic WooCommerce checkout on WordPress 7.1.5 and WooCommerce 11.3.1. A simple plus variable cart accepted the coupon and created the ₹338 Razorpay Test Mode card order. UPI selected its own method on a ₹189 Test Mode order. Both used the existing Woo order and supported reopening all Razorpay methods. A provider-hosted card modal opened with Test Mode checkout arguments. Provider capture through this WordPress order flow is pending.

The final local checkout replay used the Bricks 2.4.5 build from Plum Giraffe. A failed or stalled request moved focus to the native address form and kept the saved fields. Returning to the same address anchor after reopening the sheet preserved the checkout history. The simple test purchase reached the WooCommerce receipt and its ₹199 COD order read back as processing.

Native product and variation edits passed with the paid WooCommerce extension absent. The dashboard saved a renewal price through the normal REST route, returned it after reload and enforced the disabled-variation guard. The Kiwe Client first charge and renewal quotes are ₹8,400 and ₹700 direct, or ₹7,200 and ₹600 referred, with renewals beginning in month 13. A cart with the direct plan, a simple item, a variation and a coupon quoted ₹8,738 and the same ₹700 renewal. Razorpay Test Mode accepted that upfront total and month-13 schedule using the verified plan. That agreement was fetched and cancelled before authorization.

## Membership billing pilot

Use a dedicated local or staging environment and WooCommerce Razorpay Test Mode credentials. Set the pilot flag `KIWE_RAZORPAY_SUBSCRIPTIONS_TEST`, the merchant account `KIWE_RAZORPAY_SUBSCRIPTIONS_ACCOUNT`, and a separate webhook secret `KIWE_RAZORPAY_SUBSCRIPTIONS_WEBHOOK_SECRET` through private server configuration. Register the Test Mode webhook for captured payments, subscription charges, cancellation and processed refunds at `/wp-json/dsa/v1/razorpay/subscriptions`. The pilot reads the matching Test Mode plan and freezes the reviewed Woo order's first charge, recurring lines, renewal price and cadence before requesting a mandate. If the provider accepts the request and the connection drops, the operator reads the recorded intent and recovers the matching provider record. Each agreement covers twelve future charge cycles in this pilot. Enrollment uses unpaid orders tied to a current WordPress account, with virtual recurring lines and no renewal taxes or stock tracking. [Razorpay subscription events](https://razorpay.com/docs/payments/subscriptions/subscribe-to-webhooks) · [Webhook signature verification](https://razorpay.com/docs/webhooks/validate-test)

On MCP, **store.subscription.status** reads an eligible order's state. **store.subscription.change** requires billing permission and a fresh review for enrollment, mandate recovery or payment reconciliation. **store.members.list** reads the same permitted memberships as Daily → Users. The operations have dedicated connection scopes. The signed provider callback verifies the merchant, payment, invoice and period before Woo writes the charge. Woo stores the first charge on the original order and later renewals as linked orders. Replays keep one receipt per invoice. Refund synchronization records the verified cumulative provider refund in WooCommerce.

Daily → Users shows Active member in green and Membership cancelled or expired in red. Cancelled renewals can retain access through the purchased period. A full refund removes the affected period. Membership records do not change WordPress roles. The customer can review their own paid dates on the order. Staff need account-directory access and permission for the specific user and Woo order. The same checks gate frontend DSA and backend inbox reads, including previously stored notices. Membership notices use the private inboxes. External delivery awaits a qualified merchant policy.

Local qualification uses documented provider responses with signed callbacks and real WooCommerce orders in both HPOS and legacy storage. Hosted customer authorization, provider-originated captures, any permission-specific production rollout, member-only content controls and the shopper's recurring checkout remain to be qualified or built. Keep the current Kiwe Launch billing authority in place until hosted parity also covers referral settlement and Start access.
