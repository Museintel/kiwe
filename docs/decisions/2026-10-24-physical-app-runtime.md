# Physical Apps and native lifecycle — 24 October 2026

The founder authorizes completing the original AP01–AP06 outcomes. The accepted RC427 switches are a useful boundary, not completion of physical App distribution. Preserve those six IDs and their original acceptance properties.

Core owns the complete business brief, per-record privacy, Site Graph/MCP/Start/Seam authoring, accounts, bookmarks, security, recovery and general traffic reporting. Optional normal plugins own the SEO and Store engines. `tools/release/apps-ownership.json` is the single build ownership map. The generated `Package_Layout` identifies bundled source qualification and the physically stripped Core delivery profile; it is not a visitor setting. Normal plugins register small descriptors before `plugins_loaded`; Core admits existing engines afterward. Core files win resolution, so staging App packages alongside an older bundle cannot introduce duplicate engine ownership.

The SEO output implementation is separate from Core goals and indexing metadata. Inert search defaults and the exact conditional option writer remain in Core for complete snapshots and preboot recovery; these are data contracts, not an SEO output engine. Commerce's namespace does not imply exclusive ownership: general analytics and the essential recovery guard/session remain Core. Shared UI and native WordPress/Woo records retain their original owners.

Apps use the existing Ed25519 release trust at `app.kiwelaunch.com/apps/v1/`. The signed catalogue and signed per-App release constrain identity, API, requirements, URL, hashes and limits. Every ZIP member is verified before native extraction; installed bytes are checked afterward. Only explicit administration/native update work refreshes the small non-autoload cache. A catalogue outage never turns off installed engines. Expired or revoked release metadata cannot authorize new installation.

WordPress owns `Plugin_Upgrader`, activation, normal plugin update status, `auto_update_plugins` and its existing scheduling. Official WooCommerce is reused or installed from WordPress.org; Kiwe does not ship a Woo fork. Existing incompatible Woo requires a reviewed update. One explicit installation advances through bounded same-origin requests and can resume after closure or interruption. New shared dependencies are retained after partial completion rather than deleting another subsystem's potential dependency. The first release requires native direct filesystem access; multisite is explicitly unqualified.

A connection-scoped native lease coordinates Core and App code writers. Each App retains one immediate code original and authenticated inventory. Pending boot recovery restores code and the prior native activation choice, never an old customer/order database. Native error, interrupted staging, changed files and failed bootstrap require actual qualification; PHP lint or source assertions do not establish these outcomes.

For an existing bundled site, install/verify compatible normal App packages and native activation before replacing Core. The old bundle remains authoritative until the Core swap. A Core update's signed inner manifest declares its App API/minimum set; the updater refuses to silently drop an engine currently used by the site. SEO is recommended by default without another SEO provider, while Rank Math remains authoritative wherever present. Ascendants remains a separate actual-source migration and reviewed cutover.

The complete ledger and current limits are in [AP platform qualification](../AP-PLATFORM-2026-10-24.md). This decision is implementation architecture, not production deployment approval.

Actual native qualification finds that WordPress clears the whole `wp-content/upgrade` directory before unpacking a normal plugin. Durable App downloads, App boot markers and all App/Core recovery copies must therefore use site-bound private storage outside the document root. Core backup files retain their existing private identity through the shared location primitive; early MU recovery recognizes both strictly bounded legacy and new private locations without depending on a complete package. Ordinary requests check only known markers. The full source and native install/update/recovery proof remains an acceptance requirement.

Physical Core and runtime admission use the same generated per-App minimum versions. An original valid signature alone cannot make an older, incompatible implementation satisfy a newer Core contract.

Native WordPress interactive upgrades silently deactivate a plugin. The post-install owner restores only the previously captured activation choice and original position after verifying all new code; acceptance still waits for a fresh wp_loaded boot. Actual Core-only authoring must not instantiate disabled Store pairing services. Generic native tag groups remain in Core. Source regressions and separate native update/recovery proof are required for these boundaries.

Legacy bundled installations retain the original stable/candidate MU pointers. Physically split Core checks core-stable/core-candidate at the same trusted origin and rejects a bundled inner profile. Metadata caches are bound to delivery profile and selected channel. This prevents unmigrated sites skipping their bridge and migrated sites silently downloading the optional engines again. Publish bridge and independent pointers separately; no existing global MU feed has changed during qualification.
