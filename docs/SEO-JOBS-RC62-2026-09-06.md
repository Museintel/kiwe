## User outcome and native authority

The technical SEO workspace can start a review of posts, pages, Woo products when available, or media; inspect progress; pause, resume or cancel processing; and accept, regenerate or dismiss proposals. Each step inspects at most five records. At twenty pending proposals it waits for review. Clearing a slot and choosing Resume continues from the saved cursor. Inspection progress, eligible records, proposals, accepted native writes, dismissals, skipped records and processing errors are separate measures. The initial library count can change as records are removed or their type/visibility changes. One hundred percent inspected does not mean everything was improved, applied or ranked.

The existing `kiwe-seo` editing home still requires `manage_options`. With ownership policy enabled this is the technical owner, not the client Administrator. Client/author object-level SEO buttons and delegated review permissions remain future work; RC62 does not grant broad page, product or builder rights to make the UI available. Existing AI assistance remains the client's home for permitted SEO/SecureTrack on/off choices and read-only allowance. Provider settings and budget controls retain their original home.

SEO proposals are a Kiwe concept. Accepted fields go through `wp_update_post` and `update_post_meta` into the original WordPress fields and existing Kiwe SEO metadata, with native readback before an accepted counter is recorded. Generation never auto-applies. Source hashes include the full native copy even though model evidence is truncated. A failed or filtered write retains its proposal with an unconfirmed message; some fields may already have saved. Native hooks and multiple field writes are not one database transaction. Inspect native values before retrying; a changed record may require a new suggestion.

Private, unpublished, password-protected, uneditable and unavailable-type content is excluded before transport. Media belonging to a non-public parent is excluded too. Fresh post/parent caches and user capabilities are rechecked after provider work. Long-running broker policy refresh invalidates owner/client option caches and creates fresh Settings before evaluating permission again. Revocation discards the new suggestions. A request already dispatched may still be charged. Review also checks per-object edit permission, public visibility and the source hash before writing. A manager can dismiss an orphaned proposal without needing permission to edit a deleted object. Empty or unsupported suggestions never clear media metadata merely because the model lacks visual evidence.

## Bounded state, concurrency and recovery

`SEO_Discovery_Service` records an initial maximum ID and count for the scope. Subsequent reads use ID greater than the cursor and at most the initial maximum, ordered by ID with LIMIT at most five. No full list of IDs or OFFSET is retained. Newly inserted IDs above that boundary belong to a later job. This is a stable ID boundary, not a frozen database snapshot. The initial aggregate and each native object's own size still cost database/memory work; this is not a universal per-request memory guarantee.

`SEO_Job_Store` owns one non-autoloaded JSON option, `kiwe_seo_refinement_job_v2`, with internal schema 2. Counters, a cursor, at most twenty review proposals and one lease are bounded. Reads refuse values above 256 KiB before materializing them; writes validate shape, text sizes and total bytes. There is no custom table, queue daemon or database lock held across HTTP. Byte-exact compare-and-swap retries store-only callbacks at most five times. Provider requests and native content writes are outside those retries.

A 120-second lease serializes discovery and proposal review for one job. This exceeds the current two bounded direct HTTP attempts; it cannot guarantee completion of arbitrary WordPress AI Client implementations or native hooks. A late worker cannot commit after lease expiry or replacement. An expired operation pauses without automatic replay; an operator inspects state and resumes. An already sent request may have consumed allowance even if no result was committed. Exactly-once provider execution is not claimed.

Pause preserves a running lease and saves a completing batch's progress while leaving the job paused. Cancel preserves the lease and discards a completing generation result. Explicit review of retained proposals remains available after cancellation. Cancellation does not undo accepted native writes, delete pending proposals or cancel HTTP already sent. A new job can replace only a completed/cancelled job with no pending proposals or live lease. Accepted/dismissed proposals leave the buffer; totals remain, not an unlimited history of proposal text.

The cron hook is `kiwe_seo_refinement_batch_v2`, with job ID arguments. Normal steps wait at least 35 seconds. Early cron events reschedule at next eligibility, including when a manual step ran first. Job/proposal versions, POST, nonce and capability checks reject stale or unauthorized forms. Quota/provider failures preserve the cursor, pause, reduce the batch size, and display retry time when supplied. Resume remains manual after errors or a full review buffer. Cron availability depends on hosting/traffic; Run next step is the recovery control. Scheduling itself is not a transactional exactly-once queue.

The workspace reuses scoped task cards/CSS and reads the last stored SEO checklist snapshot. It no longer recomputes the entire score merely by opening the page or accepting each proposal. The separate existing background overall-score aggregation remains unbounded and must be redesigned before claiming all SEO work scales to arbitrary libraries. No visitor script, new CSS bundle, PWA cache or frontend SEO authority is added. Dedicated SEO plugins continue to own their frontend output.

## Compatibility and acceptance

The legacy serialized `kiwe_seo_refinement_job_v1` option is preserved, never deserialized by this worker, and not automatically migrated or resumed. A bounded existence check shows a legacy notice. Older review proposals are not copied to the new screen. A technical owner must preserve/export any wanted legacy review before adopting a new job; legacy import/review tooling is a separate gap. The old cron hook is no longer registered in RC62. Rolling back can reactivate an old queued job, so disable generation and remove only its known old scheduled hook before an intentional downgrade. Do not delete either job or the allowance ledger to bypass protection. RC61 allowance schema compatibility remains separately applicable.

Local synthetic tests exercise the actual store, discovery, refinement worker and review handlers; provider and WordPress/database operations are controlled fakes. They cover 10,000 synthetic records, CAS contention, lease expiry/fencing, pause/cancel, stale forms/content, native failures, private records, cache refresh, quota recovery and scoped UI loading. Actual MySQL contention, PHP 8.2 execution, cron scheduling failures, browser focus/responsiveness, owner policy routes, native hook/filter behavior and live provider consumption remain combined lab acceptance gaps. No responsive browser result is claimed by HTML assertions.
