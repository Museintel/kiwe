## Client promise

A mobile-friendly Backups area should explain what is protected, where it lives, when it last completed, what it excludes, and what can actually be restored. ## Hostinger findings

Hostinger's current support guide says manual backups are available on Business and higher plans, cover files/databases on the hosting plan, and can be created once per 24 hours. Its management screen exposes last/next backup dates. Verify exact account/site scope before an agency client can initiate an operation affecting other websites. [Manual backup documentation](https://www.hostinger.com/support/2298928-how-to-create-backups-at-hostinger/)

The download guide describes weekly backups for web/cloud plans, daily backups for Business and higher, six weeks of weekly copies and seven days of daily copies, with provider storage outside the hosting quota. Its automatic schedule is fixed. [Download/retention documentation](https://www.hostinger.com/support/5981435-how-to-download-backups-at-hostinger/)

The hosting agreement gives differing generic retention language and says third-party backup archives may be excluded. Treat retention as account/product evidence, display provider-reported availability and avoid hardcoded guarantees. Kiwe-created archives must have independently verified storage; do not assume Hostinger also preserves them. [Hosting agreement](https://www.hostinger.com/legal/hosting-agreement)

The installed Hostinger hosting/WordPress connector currently exposes no backup status/create/restore endpoint. This observation does not prove no API exists. Before implementing the adapter, verify an officially supported API and delegated credential scope. If unavailable, show “Provider status unavailable” plus a link to the provider panel; do not scrape hPanel passwords or invent a last-backup timestamp. Hosting detection alone cannot establish plan, enabled state, success or restore eligibility.

## Backup units and storage

| Unit | Intended scope | Restore contract |
| --- | --- | --- |
| Site recovery backup | Native database plus required WordPress, theme/plugin/MU code and selected uploads; dependency/version inventory | Whole-site restore is a privileged recovery task with preview, maintenance/concurrent-order handling and emergency access independent of a healthy plugin |
| Design/settings snapshot | Bricks templates/global styles plus explicit native WP/Woo/Kiwe configuration adapters | Allowlist exact configuration owners; remap IDs/URLs safely; do not restore orders, passwords, sessions or provider secrets as an accidental side effect |
| Media archive by date range | Attachment records, originals, derivatives, metadata and checksums; clear inclusive/exclusive dates and timezone | Restore exact attachment identity/references where possible, report missing/conflicting objects, preserve alt text, captions, srcset and image edits |
| Portable download | Manifest and verified chunks downloaded to the client's computer | Import validates schema, hashes, path/size limits and compatibility before extracting or modifying state |

A snapshot is not a full backup. The existing `Test_Site_Snapshot_Service` covers selected builder/content configuration for QA and explicitly excludes identities, orders, credentials and binaries. Audit its adapters before reuse; don't rename it into a general recovery service.

Use a resumable job/ledger with bounded batches on shared hosting, disk/inode preflight, concurrency lock, cancellation and progress. Avoid loading a multi-gigabyte archive into PHP memory. Store completed backups privately, outside public_html where possible, and encrypted before third-party upload; recovery keys need a portable client-controlled recovery path. Exclude the backup repository, active staging, logs/caches and known nested backup artifacts with a visible exclusion manifest. Use canonical path/link boundaries and archive-entry limits to prevent recursive self-inclusion, traversal and archive bombs. Ordinary ZIP/media assets must not be excluded merely for being archives.

Start with verified independent full/chunked units. Incremental or content-addressed storage needs an explicit dependency graph, retention plan and reference-aware garbage collection; deleting an older set must not break a retained one. Verify remote checksum/download and a restore drill before offering local copy removal. Retain the last usable recovery point; distinguish recovery-point age from the time an upload finished.

## Google Drive and live media

Drive is a candidate for authorized off-site backup/archive storage. Prefer app-created or explicitly selected files through `drive.file`; broad Drive access requires separate scope/verification justification. Account storage, shared-drive rules and OAuth revocation must be discovered, not inferred from a business email address. [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

Use resumable transfers and bounded exponential backoff. Google documents per-method/request quotas, a Workspace upload/copy limit of 750 GB per user per day, and additional account storage limits; these are not a public asset-delivery SLA. [Drive usage limits](https://developers.google.com/workspace/drive/api/guides/limits)

Automatic replacement of live WordPress image URLs with Drive sharing/thumbnail URLs is **not the proposed production architecture**. Drive documents browser download links and short-lived thumbnail URLs; thumbnails are explicitly unsuitable for direct web-app use due to CORS. These docs do not establish that arbitrary public image embedding violates policy, but they do not establish reliable CDN semantics either. A separate policy review is required before claiming compliance or prohibition. [Drive file reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [download API](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

Preserve the founder's disk-reduction goal through a provider-neutral object-storage/CDN adapter for actively served media, with Drive reserved as an archive/backup candidate. Selection by date is a user-facing filter, not proof a file is unused. Inventory attachment derivatives, referenced hardcoded URLs, Bricks/Woo/CSS/email exports and external inbound URLs. Verify every object before switching origin through stable attachment adapters; preview affected records, retain a fallback/cutback window and restore locally on demand. Do not perform a blind database URL replacement or delete local media immediately after upload. Offloading disk storage does not itself improve page speed.

## Sequence and acceptance

1. Provider capability/status adapter with unknown/error states and no account-wide secret exposed to client browsers.
2. Kiwe snapshot and backup inventory with manifests, exclusions, bounded jobs and a real restore drill on disposable fixtures.
3. Optional Drive upload/download provider with client-selected destination, verification, retention and revoked-token/quota tests.
4. Separate active-media offload adapter; old and new URLs, thumbnails/srcset, private media, caches, failed downloads and full local reversal must pass.

Scope-specific capabilities should distinguish viewing status, creating snapshots, exporting sensitive full backups, deleting copies and restoring site state. The client can have simple controls without automatically holding technical-owner authority over every recovery operation. Document exact consequences and permissions before implementation.
