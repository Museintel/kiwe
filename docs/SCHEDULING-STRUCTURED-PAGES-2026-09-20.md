# Scheduled publication and structured Pages — RC147 follow-up

**Accepted 20 September 2026 on the disposable Hostinger lab.** The installed Kiwe runtime remains 8.0.0-rc.147; this is a native and operational acceptance package, with no changed MU runtime files or new immutable release.

WordPress owns future-post events. The lab had no account-level scheduler before this pass. A temporary once-per-minute Hostinger task prepared one synthetic post and one Page, both due at **13:05:47 IST**. A separate Hostinger task invoked the installed WordPress wp-cron.php each minute. Without a deliberate frontend request during the timed interval, both records were published by the **13:06:02 IST** readback, 15 seconds after due. The immediate readback still saw scheduled entries; the **13:07:02 IST** readback confirmed both entries gone and both records removed. Concurrent site traffic cannot be ruled out as an additional trigger, so this proves the configured server schedule and observed timing on this lab, not exclusive causation or an exact-time guarantee on every host.

The same guarded fixture tested a synthetic Page with a Gutenberg block body, shortcode text and Bricks _bricks_page_content_2 metadata. Native rename, search-indexing change, scheduling and publish-now kept the body and builder metadata unchanged. A bounded saved-version read omitted the full body. An explicit restore changed the WordPress block body to the selected version and preserved the Bricks metadata. The builder restricts ordinary metadata writes outside its editor, so the test seeded only its synthetic builder metadata directly; Kiwe's product mutation paths never use that fixture shortcut. This covers representative installed content storage, not every extension's hooks or rendering.

The fixture is [test-wordpress-schedule-content.php](../tools/release/test-wordpress-schedule-content.php). Its nine structured-page and native-event checks passed. It is CLI-only, guarded to the disposable domain, and stays outside the MU package. The probe created no real user accounts or business settings. Synthetic records were removed, the public helper directory was moved outside public_html, and its URL now returns HTTP 404. Final readback reported debug off, RC147 loaded and the illustrated sample post/image/category intact. Homepage, sample and package manifest returned HTTP 200. [Machine-readable receipt](generated/scheduling-structured-pages-2026-09-20.json).

The lab retains **one intentional Hostinger cron job**, once a minute invoking WordPress wp-cron.php, for recurring low-traffic operation. All preparation, check and retirement jobs were removed. This is an account/site operational setting, not a Kiwe per-visitor worker. [WordPress documents](https://developer.wordpress.org/plugins/cron/hooking-wp-cron-into-the-system-task-scheduler/) a server scheduler for timely tasks on low-traffic sites and recommends disabling visit-driven spawning once the external runner is confirmed. The lab's wp-config.php was not altered here; that separate optimization belongs to the shared-host performance/operations acceptance. Future installations must verify their own scheduler, site path and tolerance before relying on timed publication.

This closes the named accounts/publishing/media/Services backend package in the first-launch forecast. Per-object SEO assistance remains in the AI/SEO packages. Other installed page extensions need explicit compatibility decisions during design delivery; a synthetic Bricks metadata check is not a universal plugin guarantee. Ascendants.in was untouched.
