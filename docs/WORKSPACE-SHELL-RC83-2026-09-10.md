# RC83: native UI bridge and editable identity

10 September 2026. Local candidate **8.0.0-rc.83**; lab remains **RC82**, Ascendants remains **RC55.4**. No live configuration, account, plugin, security or data changes. Source is uncommitted/unpushed; no signing or deployment.

The founder approved the tile prototype and clarified that the existing Design Context, dynamic tags and native business records are the foundation. The immediate work is thoughtful UI and measured speed, not rebuilding those capabilities. The subsequent reminder makes the acceptance standard explicit: move controls out of their old groups when useful; show related actions beside the subject. A category's name, content, indexing and menu placement belong to one understandable working space. The same applies to users, posts, pages, products and both kinds of category. A wrapper around old forms is a migration bridge, not the final interaction design.

## Built

[Workspace_Shell_Service](../wp-content/mu-plugins/dsa/includes/Access/Workspace_Shell_Service.php) wraps only registered Kiwe Home and the seven existing business-section callbacks in a dedicated private document. It emits no WordPress sidebar or toolbar markup. Home uses the registered WordPress `wp-element` React dependency and the existing capability-filtered task catalog; original task links render before React so a failed script does not leave an empty workspace. Context sections reuse their original PHP renderers, media picker, native POST handlers, nonce, feedback and browser-history behavior. They do not load React through this shell. This intermediate implementation uses full document navigation between native tasks, not completed SPA routing or new REST adapters.

The header reads the existing site identity and links directly to its editor. Public site rendering remains Bricks/theme-owned. No public hook, new REST route, rewrite, schema, option, permission grant or background poll is added. Existing admin enqueue/notice/footer hooks run for compatibility, including the security-enrollment reminder and media templates; their real WordPress compatibility and cost still need lab verification. The new shell assets load only on its captured admin pages. The visual palette follows the approved preview; future shared component migration must retain SEAM token authority rather than add client-owned theme settings.

Identity is redesigned beyond that wrapper: the native name and tagline are editable inside a brand area with its main logo; dark-background logo and favicon sit adjacent. Public contact facts have a direct link to their original editor. Business classification expands in place with its current summary. All eight original identity inputs, original field names and save action remain intact. The optional empty dark-logo control reads “Add dark mode logo.” Other business sections retain their original forms with the new shell presentation; their deeper interaction redesign remains work to do.

The existing category detail already links to `Navigation_Workspace_Service::url('category', id)`. Reuse this native source-aware path when designing the category working space. It does not prove that any chosen menu appears in DSA: expose verified placement from the actual binding, preserve manual menu labels, and do not invent a universal DSA visibility flag. Product-category support requires its own existing taxonomy/permission adapter review.

## Rollout boundary

The dedicated shell is **off by default**. It registers only on admin requests when the deployment configuration explicitly defines `KIWE_CLIENT_SHELL` as boolean `true`. This is a temporary engineering rollout guard, not another client setting. Keep it unset until grouped native acceptance is ready. Client role policy and current capabilities are rechecked before rendering; technical owners, subscribers, network/user admin, unrelated pages, legacy invitation entry, POST, REST, AJAX and cron keep their original handling. Removing the constant returns Home/section rendering to the original chrome. No database rollback is needed for the wrapper.

The Identity layout itself is part of the candidate's existing onboarding renderer. Full package rollback returns that view to RC82. Restore the complete previous loader/package pair, never mix versions. Native writers and dynamic tags are unchanged. The existing icon-clear behavior and required image validation are preserved rather than silently altered during UI work.
