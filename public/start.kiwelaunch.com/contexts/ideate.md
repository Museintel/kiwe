# /ideate

Start with discovery, not a fixed questionnaire. Inspect every supplied file by its contents before asking anything. Treat the attachments themselves as the source brief; do not ask the user to describe files that can be inspected.

For any supplied existing design, establish its **source authority before choosing a creative lane**. Resolve exactly one of: `approved-final`, `enhancement-authorized`, or `redesign-authorized`. Only an explicit user statement can authorize enhancement or redesign; `/ideate`, the presence of source files, visual defects, stale navigation, missing content, or the AI's preference never grants that authority. If the conversation does not prove the answer, ask exactly one question: **“Is this design final/approved, should I enhance it without changing its art direction, or are you asking for a redesign?”** Then stop. Do not select a direction, propose an art style, request SiteGraph, emit a usage brief, or create files until the user answers. If the user says only “final” or “approved,” treat that as `approved-final`.

After source authority is resolved, determine the proven lane: a new website, preservation of an approved existing design, enhancement/expansion without changing its accepted art direction, or an explicitly authorized redesign. State the detected lane and ask only for another missing decision when it materially changes the result. Never ask again for facts already supplied by the project, SiteGraph or its embedded Design Context.

Once source authority is resolved, classify SiteGraph as `required`, `beneficial`, or `not-needed` and explain the evidence. SiteGraph is required when the requested result must use or preserve real site identity, owner decisions, media, products, posts, services, menus, taxonomies, custom fields, commerce data, or future dynamic-binding intent that the supplied files do not prove completely. It is beneficial but optional for an ungrounded concept that may use honest placeholders. It is not needed when the approved supplied project is self-contained and the requested work neither introduces nor changes site-owned facts. If required evidence is absent, stop before recreation and request exactly one safe SiteGraph handoff.

Choose the safest SiteGraph connection the participating AI can actually use. Prefer an already connected read-only SiteGraph tool or MCP resource; otherwise use a scoped, expiring task-capsule/API connection; otherwise request an attached current SiteGraph export. Do not pretend an unavailable connector worked, ask the user to choose technical transport, request a broad permanent key, or paste secrets into project output. Explain the one action required only when no safe connection is available.

Inventory approved source pages, assets, references and existing-site evidence before proposing work. Existing Design Context is authoritative for business facts and owner-locked brand values; SiteGraph design content supplies real media, products, posts, taxonomies, custom content and public identity. Distinguish read-only owner facts from AI-writable suggestions.

When SiteGraph is present, report **Design Context coverage before changing any file**. Use `seamDesignContext.scores.designContextStrength` as the authoritative percentage when supplied. Otherwise calculate coverage—not subjective design quality—using this evidence rubric: identity 15%, audience and goal 10%, brand preferences 15%, public contact and localization 10%, about/founder/team 15%, pages/services/content plan 10%, commerce and product context 15%, and approved resources/media 10%. Exclude a genuinely irrelevant section and redistribute its weight proportionally; never award points for guessed values or placeholders. Show the percentage, covered sections, material gaps, locked owner facts, preserved owner preferences, AI-writable gaps, and the SiteGraph/context hash when available. If SiteGraph is not needed, record coverage as `not-applicable` rather than fabricating a number.

Next share a concise **usage brief** before changing any file. Under Design Context, list only the verified owner facts and preferences that will materially affect this requested page or project. Under Design Content, shortlist only the real products, posts, services, menus and media that have a clear intended role in the proposed result. Select media by semantic metadata, intended resource role, orientation/aspect ratio and the actual section need; do not enumerate, download or force every SiteGraph media item into the design. State what will remain dynamic, what is preview evidence only, and any ambiguity requiring review.

Then stop and ask the user to say `proceed`. Providing, attaching, replacing, reconnecting or updating SiteGraph, Design Context, source files, references or assets only satisfies an input request; it is never approval, never means `proceed`, and never authorizes file generation. After receiving any requested SiteGraph or other evidence, read it, emit the coverage report and usage brief, and stop again. Do not create or modify output files before that explicit response. The explicit response must occur after the usage brief. Emit `ideate/kiwe-ideate-discovery.json` using schema `kiwe.ideate-discovery.v4` with approval status `awaiting-user` during this pause. After `proceed`, set it to `approved`, preserve the approved source authority and usage brief as the implementation boundary, and produce the project without another generic questionnaire. A later material change to either boundary requires a new approval; small conversational corrections do not.

Do not apply Seam Framework, Bricks structures or a SEAM house style. Do not flatten unusual but intentional art direction into a component library. Keep corrections conversational until the user accepts the result.

Return a complete browser-runnable HTML/CSS/JS project appropriate to the detected lane: create a coherent new project, preserve an approved existing design, enhance it within its accepted art direction, or redesign it only when explicitly authorized. For `approved-final`, visual composition, palette, typography, spacing system, responsive behavior, content hierarchy, page boundaries and JavaScript are immutable except for explicit user corrections; SiteGraph may ground content, media and functional intent and may add non-visual semantic/dynamic markers. Never collapse multiple supplied pages into one JavaScript-switched document unless the user explicitly requests a single-file application. When a single-file application is supplied or explicitly requested, give each page view a stable unique `data-view`, `data-page`, or `data-route-view` marker so `seam.kiwe` can partition shared header/footer and page bodies deterministically. Include every required local asset and `assets/asset-manifest.json`, recording provenance and intended WordPress Media use. Preserve semantic regions and add stable `data-seam-role` markers only when they clarify meaning without changing presentation. Mark dynamic intent such as product title, price, media, contact data or repeated collections when SiteGraph proves the binding. Never invent IDs, fields, products or site facts.
